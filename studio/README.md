# Harness Studio

English | [中文](README.zh.md)

A local project workbench for requirements, screenshot references, editable four-part designs, Harness development tasks, and source delivery. Python 3.11+ serves the UI and API using only the standard library; the workbench does not require the repository's Node build.

## Run locally

From the repository root:

```sh
python3 studio/server.py
```

Open <http://127.0.0.1:3088>. Without Harness, you can create projects, upload up to four PNG/JPEG/WebP references (3 MB each), edit designs, approve a version, and inspect or restore snapshots. Case cards supply sample requirements; their images are illustrations.

The workbench prefers the adjacent Harness source checkout. Prepare the source dependencies, headless runtime metadata, and host native addon at the repository root first. A global dsh installation and Web build are not required.

```sh
pnpm install
pnpm run build:native-system
node --import tsx/esm scripts/generate-typert.ts
```

 For actual AI analysis and development, provide model credentials in the terminal that starts the workbench:

```sh
export GPT_GE_DEFAULT_API_KEY='your-default-group-key'
export GPT_GE_CODEX_API_KEY='your-codex-group-key'
python3 studio/server.py
```

An existing configured CLI can also be selected without installing another copy:

```sh
export STUDIO_DSH_COMMAND='/absolute/path/to/dsh'
python3 studio/server.py --port 3088
```

`STUDIO_DSH_COMMAND` is parsed as an argument list, never as shell code. The workbench appends `--profile headless` and sends the task on stdin. No CLI is downloaded automatically. The default launches the adjacent official CLI through Node and the tsx ESM hook, with the repository tsconfig explicitly selected so each task retains its project cwd. Only installations without adjacent source look for a global `dsh`; model selection, credentials, and tool permissions remain owned by Harness. The repository-root `.env` is not copied into generated projects; use launch environment variables or Harness credential configuration. Screenshots are supplied as local reference paths, and visual understanding requires an appropriate configured model and image-reading tool. The platform does not claim to understand a screenshot simply because it was uploaded.

## Workflow

Requirements upload accepts .docx, .md, .markdown, and .txt, with at most four staged files of 30 MB each. Uploading retains originals in the local requirement-uploads cache and does not call AI or insert document text into the supplemental-input field. The browser stores lightweight attachment IDs and supplemental text for refresh recovery. Cache references expire after 24 hours; a later upload removes expired copies, and Remove deletes the selected staging copy. A 512 MB cache quota bounds abandoned uploads. Do not treat this single-user loopback cache as authenticated team storage.

Word staging preserves main-document paragraphs and embedded image references in order, with paragraph-number and image markers. PNG/JPEG/WebP images become local image-tool inputs. Unsupported picture formats are retained but reported, and external images, charts, SmartArt, or embedded objects require supplemental screenshots; they are never fetched automatically. Headers, footers, comments, and page layout remain in the original rather than the text extraction. Word expanded content is bounded to 120 MB, main XML to 30 MB, each image to 30 MB, and unique images to 80; extracted text remains limited to 30,000 characters per file. Markdown external/local-path images also require separate screenshots.

Click Start my project, name the project, and confirm Create and analyze to save original attachments, supplemental text, and screenshots together and enqueue analysis. Document-only projects are supported. Creation requests carry an idempotency ID so retrying the same intake does not create a second analysis task; changed intake needs a new ID. An analysis-start failure leaves the project and documents saved with an actionable message. Project attachments are separate copies, unaffected by removal or expiry of staging copies, and can be downloaded from Original requirements. A new job copies originals, ordered text, and image metadata into its private workspace exchange; the analysis prompt requires actual reading of supported images and disclosure of unread/unsupported content. Model and gateway image support must still be verified; successful upload does not establish image understanding. Raw attachments are excluded from source delivery ZIPs. Restart HTTP and Worker to use the complete attachment workflow.

Create a project with requirements and optional references. Generate a design using Harness or create a manual draft. Each design has PRD, frontend, backend/API, and database sections. Edit original text directly or submit feedback against a section or the whole project. Saving a design creates a snapshot and cancels previous approval and build eligibility; stale editors are rejected.

Confirm the reviewed version, then explicitly start development. The developer receives that version and writes source files in the project workspace. Inputs, reference copies, and results live in `.studio/<job ID>/` inside the project workspace; the supervisor validates and collects results without requiring the agent to write outside its workspace. Submission returns HTTP 202 with a persisted task identity. An independent Worker claims tasks in order; one Harness task executes at a time per data directory. Same-project changes may explicitly join a queue of at most ten pending tasks, bound to the submitted design version. Failed, cancelled, interrupted dependencies or a changed design block followups for review rather than silently using stale inputs. Tasks expose actual exit status, timeout, cancellation, and validation failures; an exit-zero process without the expected result file cannot complete a task. Feedback and complete design snapshots survive a restart. Restarting HTTP does not interrupt the independent Worker. SSE streams factual execution stages and replays missed states by event cursor. Interrupted Worker tasks have an unknown outcome and are not automatically replayed. Task history under Versions provides logs and explicit retry against the current design; retries do not roll back source files.

Preview starts in experience mode, preserving the page's buttons, inputs, tabs, and dialogs. Switch to element inspection to open feedback with the element tag, visible text, CSS selector, and page path; press Escape to return to experience mode. Switching modes does not reload the page. These hints do not guarantee a source-code mapping, and the side panel still accepts direct text feedback.

Opening Development and preview automatically starts the isolated runtime when prerequisites pass and no task is active. The workbench displays the actual running frontend; static preview and Stop controls are absent. Missing prerequisites or startup failures remain visible with checks, logs and an explicit retry. Failed starts are not retried in a loop. Manual development submissions and workbench shutdown stop the owned preview; assistant questions and background edits preserve it. Standalone `preview.html` may remain in generated files, but it is not displayed as a runtime fallback.

Run preview supports Python ASGI applications with Alembic and installed dependencies on macOS. It recognizes `backend/app/main.py`, `.venv/bin/python`, and `frontend/index.html`. Other layouts can provide the following workspace `studio-preview.json`. The adapter runs `python -m alembic upgrade head` and Uvicorn, then serves the frontend and an owned `/api/` proxy on a separate local origin after a successful health check. It neither installs dependencies nor supports arbitrary stacks.

```json
{"kind":"python-asgi","cwd":"backend","python":".venv/bin/python","app":"app.main:app","frontend":"frontend","health":"/api/v1/health"}
```

Run preview uses the project's `preview-runtime/<channel>/preview.sqlite`, retained after stopping. `sandbox-exec` confines file access and writes and denies external networking; root-directory reading matches only `/` itself, excluding descendants. Model credentials are not inherited. The environment sets `AUTH_ENABLED=false`, `SCHEDULE_ENABLED=false`, `DISPATCH_ENABLED=false`, and `LLM_PROVIDER=extractive`; applications must honor these settings. Frontend requests are restricted to same-origin APIs. Use preview logs to diagnose startup failures; unmet platform or dependency requirements remain visible in runtime checks. Manual development stops the running preview; assistant edits use retained private drafts while the published preview continues. Workbench shutdown also stops previews, while independent Workers continue.

Confirmed projects with saved source can run in preview while review is pending; acceptance and export remain restricted. Source review excludes browser installations, download caches, build output, and private databases from both hashing and the review copy. Standard-library HTTP applications may use `{"kind":"python-http","cwd":".","script":"server.py","frontend":"public","health":"/api/v1/health","cookieNames":["mine_demo_session"]}`. The script must adopt the listening socket descriptor in `STUDIO_PREVIEW_FD`; `PORT` identifies that socket and `DATABASE_PATH` selects the isolated preview database. Without a configured Python executable this adapter uses Studio’s Python. Only listed session cookies are proxied, with per-preview names; idempotency and conditional-update headers are preserved.

The project assistant follows the page context: Design discusses or modifies the design, while Development and preview discusses or modifies code. There is no manual mode selector. An agent first evaluates each message on a disposable filtered source copy; questions, diagnosis, discussion and ambiguous requests receive answers, while explicit change requests create a separate guarded design/code task. Code changes require the confirmed design and run in a retained `assistant-drafts/<job>` source copy. Failure or cancellation leaves published code and preview unchanged. Renaming, including Previous conversation, persists without changing messages or model context; a stale title cannot overwrite a newer name. New conversation creates a durable empty conversation without a model request. Old ungrouped messages appear under Previous conversation. New automatic-intent messages require Worker capability `projectChat: 3`; finish active work and restart HTTP and Worker after upgrading. The browser checks HTTP `assistantProtocol: 3` before sending a message; stale servers reject locally without stopping preview. Question interpretation depends on the configured model, and an unclear request should ask for clarification.

The composer model selector applies to the next submitted task, using model IDs declared by the routing policy, its fallback, or the deployment assistantModels list. A compact dark popup selects low, medium, high, xhigh, or max reasoning, defaulting to high. The selected effort is saved with the project draft, snapshotted into the next task, and inherited by assistant-created modifications and their reviews while preserving stage groups; selecting a model does not change an already queued task or the global policy. Speech input uses the browser's SpeechRecognition API with Chinese transcription, may use the browser vendor's online recognition, and requires microphone permission. Unsupported browsers and denied permissions retain the text draft and show an explanation. Transcription is editable and never auto-submits; navigation and sending stop recognition. Enter sends, Shift+Enter adds a line, and IME composition does not submit.

Feedback mode, model, text, selection, recent tab, and section-edit drafts use browser-local storage per project. This is not a server backup: clearing browser data or switching browsers does not restore drafts. Storage failures appear in place. Successful submission clears only the submitted feedback; closing a dialog retains drafts. An edit draft from an older version cannot overwrite the current design; copy its text, discard the draft, and reopen the editor. Manual-template placeholders must be completed before approval or development submission.

Switching tabs within a project preserves the mounted preview iframe and its in-memory state. Explicit refresh, preview-source changes, publishing a ready runtime replacement, opening another project, or browser refresh still reload the preview; unsubmitted forms inside previews are not workbench text drafts. Preview readiness checks read configuration and files without executing application code. Missing prerequisites disable startup and remain visible. Dependency imports, migrations, and health checks are verified during startup.

System iterations explicitly select style adjustment or business/interaction development, defaulting to business. The route is saved with feedback and preserved across navigation and retries. Style adjustment requires a completed development version and does not regenerate the PRD. Execution uses a separate temporary copy containing existing frontend CSS, HTML, and feedback, without full requirements, the four-part design, references, backend, or database files. Eligible locations are `frontend/`, `client/`, `web/`, `src/`, `public/`, `assets/`, and the workspace top level; hidden directories, dependencies, and symlinks are skipped. Each file is limited to 2 MB, with a 10 MB total. HTML changes are restricted to CSS inside existing style elements; tags, attributes, scripts, other markup, file additions, and deletion are rejected. Component-local JS/TSX styles, APIs, authorization, databases, and interactions use business development.

Tasks use an overlay that disables default skill discovery and exposes only the skills assigned to their stage. This does not install third-party Cordis plugins. Business development verifies affected frontend, API, and database behavior without redoing requirements analysis for every small edit. Before transfer, the service validates scope and checks that original files remain unchanged. Out-of-scope tasks fail without publishing their copy; models can also return `needsBusiness: true` to request an explicit route change. Successful style tasks require renewed final acceptance. Failures before any transfer attempt retain the previous development and acceptance eligibility. Harness owns process confinement; copies and file validation do not replace its execution sandbox. Deterministic fixture tests do not establish correct skill usage by a real model.

When upgrading task routes, wait for active tasks to finish, request the old Worker to stop, confirm it has exited, then restart HTTP and Worker and refresh browser tabs. Existing queued tasks do not change routes automatically; old tasks without a declared route use business development.

When existing code is present, the development button opens a choice. Fresh development retains the entire workspace under `workspace-backups/<job-id>/` before installing a blank workspace with only the task inputs. Backups include local settings and data, stay on this computer outside delivery ZIPs, and have no automatic expiry. Do not share them without checking their contents. If a directory swap is interrupted, the next Worker restores the retained workspace when the active directory is missing. ## Model stages and review loop

The optional `fallback` policy selects `from`, `to`, and `primaryRetries`. New GPT tasks retry `gpt-6.1-sol` once, then resume the same persisted Session with `gpt-6-sol` after a terminal transient model error. The existing two-minute initial retry delay remains. Authentication/configuration failures, cancellation, deadlines, missing Session identity, unreadable progress, and tools without results stop without fallback. The fallback model uses the provider’s bounded retry policy; no switch back occurs within that stage. Every stage uses its configured provider group and reasoning effort, including fallback calls. New stages start from their configured model. Model availability requires gateway validation; queued policies without fallback retain their original behavior.

`model-routing.json` selects the provider, analysis, development, and review models. All stages default to `gpt-6.1-sol`. `stageProviders` selects `gpt-ge-default` for analysis/design revisions and `gpt-ge-codex` for development/repair/review; `reasoning: high` is the default for every stage and fallback model; an assistant submission can override it for that task. New tasks snapshot the policy. `reviewMode: focused` is the default with `maxReviewRounds: 2`: at most one repair followed by targeted verification. `reviewMode: full` retains the legacy repeated full-review workflow; queued policies without reviewMode retain that behavior. Model and gateway availability require separate real-provider validation.

Focused tasks parse available Python/JavaScript syntax and package JSON before model review, without running application code. Checks cover at most 50 files and 20 JavaScript files of at most 1 MB each, and do not prove build, runtime, or deployment readiness. A detected syntax failure goes to repair before spending a model review. After a valid development result, static preview becomes available during review. First builds and detected authorization/database changes receive a full review; other iterations review changed files and direct consumers. A repair's recheck receives previous findings and verifies those plus related regressions rather than starting another full audit. Changed-file detection and model severity judgments do not guarantee complete risk detection.

The retained-code review notice appears only in Development and Preview after a development result is available and review remains pending or blocked. Execution Status shows task progress without this notice.

Reports distinguish critical/high/medium blockers, failed checks, low advisories, and missing evidence. Blockers and unverified results retain source and preview but prevent final acceptance and export; ordinary advisories do not block manual acceptance. Review failure does not label completed development as a failed task. Development or repair execution failure, cancellation, and timeout still stop the task and retain files for inspection. Review copies exclude dependencies, private files and databases; missing prerequisites must be reported. Reports are model evidence, not platform certification. The existing task deadline covers all calls and checks; no monetary cap is enforced. Style-only changes retain their isolated fast path.

Use Continue fixing review findings to submit the previous report with the existing workspace, including for a legacy failed task whose report still matches the current design and source run. Stale reports are refused. After a local-change review, use Pre-delivery full review in Delivery before final acceptance; it reviews current source without an initial development call. Initial full reviews and isolated style-only changes do not require a redundant full review. Inspect reports and local check results before manual acceptance. The HTTP acceptance and export endpoints enforce these rules independently of disabled buttons.

Restart HTTP and Worker after active work finishes; focused tasks require a matching focusedReview capability marker. Existing queued tasks retain their saved policy. Optional reviewState, reviewStatus, scope, finalReview, and localChecks fields require no SQLite schema or Harness Session migration.

## Delivery and limits

Source export requires a successful development result for the approved design, user confirmation of that final development run, and the presence of `README.md`, `Dockerfile`, `compose.yaml`, `.env.example`, and `VALIDATION.md`. The ZIP contains source, design, and an explicit deployment verification notice. It omits `.env*` other than `.env.example`, dependencies, Git metadata, the `.studio` task exchange directory, symlinks, common private-key files, and databases named with `.db`, `.sqlite`, or `.sqlite3` and their `-wal`, `-shm`, and `-journal` companion files. Inspect source before sharing: the exporter cannot detect arbitrary secrets embedded in code.

Docker deployment, backend integration, automated acceptance, cross-linked design changes, and source-code version rollback are not independently verified or implemented by this workbench. Design snapshots support restore-as-new-version; generated source uses one mutable workspace and failed runs may leave partial edits. The development prompt requests tests and deployment instructions, but task completion and file presence do not certify a functioning deployed application. Real model execution requires working Harness configuration and has not been verified by the deterministic tests.

The server binds only loopback and enforces same-origin JSON writes and an exact Host header. It is a single-user development tool with no account authentication or team isolation. Separate project directories are not an execution sandbox: Harness owns tool confinement, and only trusted local users should start tasks. Do not expose this service through a public port or tunnel.

## Data and settings

Projects, screenshots, design history, requests, task logs, and generated source live under `studio/.data/` by default and are excluded from Git. Projects, jobs, and SSE events are authoritative in `studio.sqlite`. First startup imports legacy `*/project.json` transactionally and preserves those files as unchanged backups. Stop the old server and its tasks before migration. Existing workspace and screenshot locations stay unchanged. Do not run older Studio versions against migrated data or edit JSON expecting the UI to update. `STUDIO_DATA_DIR` selects another data directory. `STUDIO_JOB_TIMEOUT` sets the task timeout in seconds (default 1800). `--port` selects the HTTP port (default 3088). Keep one HTTP process per data directory. Ctrl+C stops only HTTP; the independent Worker keeps running. An exclusive file lock prevents duplicate execution and is inherited by the Harness child: after a Worker crash, a surviving child prevents a replacement executor until it exits. Missing heartbeats produce an offline notice while queued tasks remain stored. Inspect `worker.log` and surviving children before starting a replacement. Tasks with unknown outcomes are never automatically retried.

Stage model overlays retain the provider protocol, endpoint, and credential environment variable from `harness.patch.yml`. This file uses JSON syntax, a valid YAML subset; never put actual keys in it.

Temporary overload, rate limits, transport drops, timeouts, and empty responses retry the failed model step within the same live Harness session. The GPT.GE route allows three retries, waiting 120, 240, then 300 seconds; edit `retryPolicy` in `harness.patch.yml` to change this. The task deadline includes these waits, and cancellation or Worker shutdown stops recovery. The status panel shows the retry count and countdown. Authentication, quota, invalid requests and unknown errors do not retry. Completed tools are not replayed by restarting the whole task; failed partial responses are discarded and the request is reconstructed from committed history. A killed process or restarted Worker still requires an explicit retry because its outcome may be unknown. Every provider retry may incur token charges; this is not a monetary budget. Restart Worker after changing this policy.

## Worker management

The default startup starts or reuses an independent Worker. To manage the two processes separately, run this in a terminal with model credentials:

```sh
python3 studio/server.py --worker
```

Run HTTP in another terminal:

```sh
python3 studio/server.py --no-worker
```

Request Worker shutdown using the same data directory:

```sh
python3 studio/server.py --stop-worker
```

This requests interruption of the current task while preserving files and queued work. The default background Worker writes diagnostics to `worker.log`; per-project task logs use `job-<job ID>.log`, and legacy `run.log` remains readable. After changing model credentials, stop and restart the Worker: it does not inherit updated environment variables from a restarted HTTP process. Changing `STUDIO_JOB_TIMEOUT` affects newly submitted tasks; existing tasks retain their submitted limit. Stop HTTP and the Worker before backup, and copy SQLite and its companion files together with project directories.

## GPT.GE

The workbench automatically loads `harness.patch.yml` to connect through Chat Completions at `https://api.gpt.ge/v1`; stage selection follows the model policy described above. Set `GPT_GE_DEFAULT_API_KEY` and `GPT_GE_CODEX_API_KEY` in the launch terminal to two different tokens, each bound only to its named group with automatic grouping disabled in GPT.GE. Group selection belongs to the gateway token, not the model ID or a fabricated request header. Missing stage credentials fail without trying the other group. `GPT_GE_API_KEY` is retained only for older queued policies that select the legacy route; do not put credentials in YAML. Model availability, protocol support, and account route permissions remain subject to the gateway. Local configuration validation does not verify account access. Restart HTTP and Worker after active tasks finish; new policies require the `stageRouting: 1` capability. Queued policies retain their saved model, provider, and reasoning selection. Local tests verify the outgoing high reasoning field and separate credentials, not the gateway account’s token-group binding or model availability.

The runtime proxy streams uploads in 64 KiB chunks. `studio-preview.json` accepts `maxRequestBytes` (default and maximum 600 MiB) and `requestTimeoutSeconds` (default 120, maximum 600), plus `maxResponseBytes` (default 64 MiB, maximum 600 MiB) for decoded backend responses. Oversized responses return PREVIEW_RESPONSE_TOO_LARGE with a traceId instead of HTML. Proxy failures and large response sizes are recorded in the preview log without payloads, credentials or query strings; restart the runtime preview to apply configuration changes. Browser disconnects close the response without attempting another error response. Oversized uploads and proxy failures return JSON errors; application GLB geometry and format limits still apply. A successful upload is not evidence that the model passed validation.

Projects with imported requirement documents retain the selected page text when submitting assistant questions; attachment directories do not replace the conversation target.

The assistant uses a single rounded composer with image and page-selection cards above the message. Each card can be removed independently; the plus button accepts up to four PNG/JPEG/WebP images, each at most 3 MiB, and up to eight page selections are sent as separate contexts. Conversation titles and scope explanations are absent above the composer; the triangle retains conversation navigation and rename actions. Attachment drafts are local to each conversation; browser storage failures remain visible. Submitted images persist with the message and are copied into the assistant’s disposable task directory for actual reading. Image messages require HTTP chatImageAttachments: 1 and Worker projectChat: 4; restart both after active work finishes. Model image-reading capability still determines whether images can be understood.

`assistantModels` is a deployment allowlist for the composer, currently including `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, and `claude-sonnet-5-5`. It is excluded from durable execution policies; submitted tasks retain their selected model and effort. HTTP and Worker advertise `reasoningSelection: 1`; restart both after current work finishes to use all five levels. Local wire fixtures verify the outgoing model and reasoning_effort fields, not gateway availability or permissions for a model/effort combination. Unsupported combinations must be reported by the gateway without silently reducing the selected effort.

Drag photos or files onto the project assistant, or use the plus button. The file picker accepts all file formats, including GLB, PDF, ZIP, audio, video and extensionless files. PNG/JPEG/WebP photos up to 3 MiB produce thumbnails; larger photos and other formats produce ordinary name/size cards, each removable independently. Up to four preview photos and four ordinary files may be attached, with a 64 MiB combined limit; folders are rejected. Failed reads, oversized drops and submission errors retain the text and previous attachments. File drafts belong to their conversation; large browser-storage writes may fail visibly and require reattachment after refresh. Submitted originals persist outside the application workspace in `chat-files/<job>`, remain downloadable in history and are copied into the assistant task. Supported Word/Markdown/text files additionally use the existing bounded text extractor; other files are supplied as originals and unsupported binary parsing must be reported rather than claimed as understood. File messages require HTTP and Worker chatFiles: 1; restart after active work finishes. The jobs endpoint accepts at most 90 MiB JSON to carry bounded base64 attachments; other endpoints retain their limits.

During an assistant task, the square button interrupts only the current conversation’s task. Sending another message queues it in a compact row above the composer, with a delete button to cancel that queued message and remove its user/reply entries from conversation history and subsequent model context; its Guide button atomically saves a continuation, cancels the current round and the selected queued message, and gives the continuation priority after the owned process exits. The continuation includes the original goal, the new instruction, attachments, conversation history and published code; conflicting new instructions take priority. This starts a new Harness call, not an exact restoration of model reasoning. Unpublished code drafts stay on disk and are not automatically reused or published. Other queued messages stay queued. Duplicate Guide requests reuse the saved continuation; invalid or failed submissions leave the original tasks unchanged. HTTP and Worker require assistantSteering: 1; restart both to enable guiding. Published preview remains usable during interruption and guiding, and changes appear after successful publication.

Code questions include up to 8 KiB of preview logs and the configured proxy limits; configuration values do not establish which settings an already running process uses. Reviews copy explicitly submitted file attachments into their disposable workspace and rewrite paths, so binary fixtures remain available despite source-code filtering. Missing capabilities or files must still be reported as unverified.

Critical, high and medium findings enter the existing bounded repair/recheck loop; low findings remain advisories.
